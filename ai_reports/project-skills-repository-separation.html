SpecKit-SSD-SDLC · Migration Report

Separating framework skills from project skills

Move the tech-stack pattern skills out of the framework and into a project-owned git repository laid out as a Claude Code plugin marketplace — auto-synced, scope-attachable, and updatable by Claude itself through pull requests.

Date 2026-08-23 Status Proposal / roadmap Effort ~4 dev-days

1Executive summary

Today .claude/skills/ ships two fundamentally different kinds of skills together, distributed by git subtree + setup.sh rsync:

  • FRAMEWORK  The 23 sk.* pipeline skills plus governance/ — stack-agnostic SDLC machinery that should be overwritten on every framework update.
  • STACK  ~24 pattern skills (backend-architecture, nextjs-patterns, data-access-patterns, …) that encode one project's chosen stack — .NET 10 seam architecture, FastEndpoints, Next.js, React Native. These are project assets wearing framework clothing.

The proposal: move the stack skills into a separate, private GitHub repository structured as a plugin marketplace (.claude-plugin/marketplace.json + one folder per plugin). That unlocks the capabilities in Anthropic's “Set up a skills repository Claude can update”: merge-to-sync propagation, Claude-authored skill PRs with a human merge gate, and one skills repo serving Claude Code, claude.ai, and Claude Tag at once.

The framework already states the rule this completes — backend-architecture §1: “Skills carry grammar, project memory carries vocabulary.” The split adds the missing tier: framework carries process, skills repo carries stack grammar, project memory carries vocabulary.

2.2 Why the current model hurts

  • setup.sh runs rsync -a --delete over .claude/ — any project-local skill edit is destroyed on every framework update. Projects cannot safely evolve their own pattern skills.
  • A second project on a different stack would inherit 24 irrelevant .NET/React skills and have to fork the framework — defeating the subtree-update story.
  • Skill improvements learned during real work die with the session. There is no channel for “that worked — remember it” to persist into the skills.

3Target state

3.1 Three-tier ownership model

Tier 1 — Framework SpecKit-SSD-SDLC

Process: sk.* pipeline, governance, memory-loader skills, agents, hooks, templates, setup.sh. Stack-agnostic. Updated via git subtree pull. Changes rarely.

▲ pins process  ·  ▼ supplies stack grammar

Tier 2 — Skills repo NEW · e.g. <org>/dotnet-react-skills

Stack grammar: the 24 pattern skills bundled as plugins in a marketplace layout. Private GitHub repo. Auto-syncs to claude.ai; pinned as a marketplace in each project's .claude/settings.json. Claude opens PRs against it; humans merge. Changes when the team learns something.

▼ references vocabulary via placeholders + pointers

Tier 3 — Project repo

Vocabulary: .specify/memory/ (system-context, standards, auth contract, observability stack), specs/, knowledge bases, session.yaml, and the settings pin for Tier 2. Changes continuously.

3.2 Skills repository layout

dotnet-react-skills/                      # private GitHub repo
├── .claude-plugin/
│   └── marketplace.json                  # lists each plugin
├── backend-dotnet/                       # plugin 1
│   ├── .claude-plugin/plugin.json
│   └── skills/
│       ├── backend-architecture/SKILL.md # canonical SSOT, moves intact
│       └── backend-feature-patterns/…   # + 8 more backend skills
├── data-dotnet/                          # plugin 2: data-access, caching,
│   └── skills/…                          #   search, file-pipeline
├── frontend-web/                         # plugin 3: nextjs, react-admin,
│   └── skills/…                          #   design-system, a11y, zustand…
└── frontend-mobile/                      # plugin 4: react-native-patterns
    └── skills/…

Why four plugins, not one or twenty-four: plugins are the enable/disable unit per scope. A backend-only service enables backend-dotnet + data-dotnet; the mobile channel enables frontend-mobile. The four bundles mirror the existing CLAUDE.md table sections.

What does not move: .specify/memory/* stays in each project. The inject_files pointers from pattern skills to project memory resolve against the consuming project's root and keep working unchanged.

Resolution after the split: plugin skills surface as plugin-name:skill-name but each skill's own name: frontmatter is untouched, so descriptions and triggers survive. Framework routing switches from paths to names — the one change that makes the framework genuinely stack-agnostic.

5Migration roadmap — ~4 dev-days

Phase 0 — Decisions & prerequisites ½ day

  • Confirm the §2.1 classification (design-principles stays framework; accessibility-standards ships in frontend-web).
  • Name the skills repo after the stack, not the project (dotnet-react-skills) — the placeholder convention already makes it reusable across same-stack projects.
  • Checklist: private repo · GitHub connector enabled · Claude GitHub App linked · admin access to claude.ai Plugins + Access bundles.

Phase 1 — Create the skills repository 1 day

  1. Scaffold marketplace.json + four plugin folders, each with plugin.json + skills/.
  2. Copy the 24 pattern skill folders unchanged — same names, same frontmatter, same memory pointers.
  3. Fix the one intra-family inject (data-access-patterns → sibling skill) as a plugin-relative reference.
  4. README states the contribution contract: the grammar test from backend-architecture §1 — no project facts.
  5. Optional: CI running skill lint / plugin eval on PRs, so Claude-authored PRs get automatic feedback.

Phase 2 — Decouple the framework 1–2 days · the real surgery

  1. Routing tables → name-based manifest. Replace literal paths in the nine prompt files with skill names, and move the keyword→skill tables into project memory: .specify/memory/skill-routing.md. Framework prompts say only “load the skills the routing manifest selects for this role + story tags”.
  2. CLAUDE.md template split — remove the tech-stack tables; the skills repo ships a fragment that sk.init merges in.
  3. setup.sh guard — warn on leftover pattern-skill folders in .claude/skills/ that would shadow plugin versions.
  4. Archive moved skills via the mandated archive-file.sh flow (no rm; human reviews the log).
  5. Teach sk.init to record the marketplace repo in project-config.md and scaffold the settings pin.

Phase 3 — Wire up consumption ½ day

Claude Code — check into each project's .claude/settings.json (validate exact key shape against the current CLI at rollout):

{
  "extraKnownMarketplaces": {
    "dotnet-react-skills": { "source": { "source": "github",
                             "repo": "<org>/dotnet-react-skills" } } },
  "enabledPlugins": {
    "backend-dotnet@dotnet-react-skills": true,
    "data-dotnet@dotnet-react-skills": true,
    "frontend-web@dotnet-react-skills": true,
    "frontend-mobile@dotnet-react-skills": true }
}

claude.ai / Claude Tag — Admin → Plugins → Add plugins → Sync from GitHub (auto-sync on) · Access bundle → Repositories (write for PRs) · bundle → Plugins tab → toggle the four plugins.

Phase 4 — Turn on the improvement loop ½ day

  • Prompt convention: “open a PR to the skills repo updating <skill> with <learning>”.
  • Weekly routine sweeping corrections into one consolidated PR.
  • Review discipline: grammar test, placeholder convention, plugin eval — then merge and verify a fresh session picks up the change.

Phase 5 — Cleanup & docs ½ day

  • Update framework README (Quick Start gains a “pin your stack's marketplace” step) and docs/memory-guide.md with the three-tier model.
  • Prune migrated-skill Edit(...) entries from the settings allow-list; tag a framework release; projects subtree-pull + add the pin.

7Recommended decisions

  1. Split now — only ~9 prompt files + the CLAUDE.md tables need surgery; injects and placeholders already support it.
  2. Four plugins mirroring the existing table sections: backend / data / frontend-web / frontend-mobile.
  3. Name the repo by stack, not project, to collect the reuse the placeholder convention already paid for.
  4. Routing manifest in project memory, shipped from the skills repo — the piece that makes SpecKit adoptable by any stack.
  5. Governed loop: Claude proposes, CI evaluates, a human merges — consistent with existing checkpoint and archive policy.
